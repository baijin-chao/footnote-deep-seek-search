# Deep Research Agent · 迭代路线图

> 版本 v0.1 ｜ 配套文档：[00-pre-dev-spec.md](./00-pre-dev-spec.md)
> 说明：本文所有指标均为**目标值**，不是实测值。M5 评测集建好后回填真实基线，并保留"目标 vs 实际"的差距——这个差距本身就是面试素材（说明你会做估计，也会承认偏差）。

---

## 0. 一句话回答"几次迭代"

**5 次**：4 次核心迭代（V0→V4）+ 1 次可选加分（V5）。核心约 **15 人日**，按每天 4–5 小时有效投入，约 **3 周**。

每次迭代必须满足三个条件，否则不算迭代、只能算"改了点代码"：

1. 有一个**明确的失败模式**作为出发点（来自 trace，不靠感觉）
2. 有**可对比的指标变化**（跑同一套题，前后对比）
3. 有一个**能在面试里讲 2 分钟**的技术决策

---

## 1. 迭代总览

| 版本 | 主题 | 解决的问题 | 工期 | 成功后的一句话 |
|---|---|---|---|---|
| **V0** | 能跑通 | 没有基线，无从优化 | 2.5d | "先做出能跑的最小闭环，拿到 45% 的难看基线" |
| **V1** | 能可靠 | 引用是编的、JSON 解析炸、抓取失败就崩 | 3d | "把'不可测'变成'可验证'，引用支持率 88%" |
| **V2** | 能解释 | 不知道错在哪，调 prompt 靠玄学 | 3d | "有了 trace 和 50 题评测集，失败能被归类" |
| **V3** | 能聪明 | 覆盖不全、上下文膨胀、成本失控 | 3.5d | "反思回环 + 上下文工程，步数 18→11，成本腰斩" |
| **V4** | 能交付 | 只有 CLI 没法演示，失败要重跑 | 2.5d | "SSE 流式 + 断点恢复，3 分钟 demo 站得住" |
| **V5** | 能加分（可选） | 缺"多 Agent 是否有必要"的实证 | 2–3d | "对照实验证明：这道题单 Agent 更划算" |

## 2. 各迭代详情

### V0 · 最小闭环（2.5 人日）

**要解决的**：没有基线，后面所有优化都是玄学。

**做什么**

- 状态机 `INIT→PLAN→GATHER→REFLECT→WRITE→DONE` 串行跑通
- Planner 出 3–6 个子问题；每个子问题 search → fetch → 抽取 → 存 evidence
- Writer 直接拼装 evidence 摘要成报告
- SQLite 落库，CLI 一条命令出 markdown

**技术栈**：Python 3.12 · httpx · 自研状态机 · SQLite · trafilatura · DeepSeek(OpenAI 兼容) · 纯 stdlib 日志

**预期效果**：能出报告，但质量很差——成功率约 **45%**，平均 **18 步**，P95 **180s**，单次成本 **¥0.9**，引用**无法验证**（都是模型自己写的序号）。

**面试怎么讲**：讲"我先做基线，不追求好看"。绝大多数候选人的项目没有基线，这一步就把你和他们区分开了。

**DoD**：`run.ps1 "问题"` 产出报告 + 一条 baseline 指标记录。

---

### V1 · 可靠性工程（3 人日）

**要解决的**（全部来自 V0 的失败观察）：引用是编的；LLM 偶尔不按 JSON 输出；任意一次抓取失败整个 run 挂掉。

**做什么**

| 问题 | 手段 |
|---|---|
| 引用幻觉 | evidence 存正文 + 偏移；生成后**回填校验**，claim 与原文片段不匹配则降级为 `[未证实]` |
| 结构化输出不稳 | pydantic 校验 + JSON 修复重试（1 次）+ 仍失败则模板降级 |
| 单点失败中断 | provider 级降级（Tavily→备用源）、抓取失败标 `fetch_failed` 继续、超时与重试退避 |
| 死循环/失控 | 四重终止：finish 信号 / 步数 / 预算 / 连续两轮无新 evidence |

**技术栈**：+ pydantic schema 校验 · function calling / JSON mode · 指数退避重试 · 多 provider 降级链

**预期效果**：成功率 **45% → 62%**，引用支持率首次可测 **88%**，崩溃率 **0**，平均步数略降 16。

**面试怎么讲**：这是最高频追问"你怎么防幻觉引用"。答法不是"我加了 prompt"，而是"引用必须能被原文验证，验证不过就标未证实"——这是工程手段，不是提示词技巧。

**DoD**：故意构造 3 条错误引用，全部被正确标记；抓取失败场景不中断。

---

### V2 · 可观测 + 评测集（3 人日｜**分水岭**）

**要解决的**：不知道错在哪。V1 之后成功率卡在 62%，但完全不知道该改哪里。

**做什么**

- span 树埋点：每次 LLM 调用、搜索、抓取都是 span，记录耗时/ token /成本/父子关系
- 50 题评测集（事实 15 / 对比 10 / 时效 10 / 多跳 10 / 无解 5）
- 跑批 harness：一条命令跑全量，输出指标表 + HTML 报告
- LLM judge 初筛 + 人工抽检 20 条校准（一致率 < 85% 就改 judge）

**技术栈**：+ 自研 trace（字段对齐 OpenTelemetry GenAI 语义约定）· pytest 参数化跑批 · judge prompt · Markdown/HTML 报告

**预期效果**：成功率 **62% → 70%**（部分靠"被测出来了"——之前默默失败的 case 现在被计入并逐个修掉）。首次能给出失败分布：

| 失败类型 | 占比 | 说明 |
|---|---|---|
| 检索空白 | ~40% | 子问题搜不到有效结果 |
| 子问题拆错 | ~30% | 拆得太宽/太窄 |
| 长文截断 | ~20% | 正文抽取后关键段丢失 |
| 其他 | ~10% | 输出格式、超时 |

**面试怎么讲**：**这是整个项目的转折点**。面试时打开一条失败 trace，说"这里的搜索返回了 8 条结果，但 reader 只截取了前 2000 字，关键段落被切掉了——这是我 V3 要做的事"。这一分钟的说服力超过十页 PPT。

**DoD**：一条命令出指标表；能画出失败分布饼图；judge 与人工一致率 ≥ 85%。

---

### V3 · 智能与成本（3.5 人日）

**要解决的**：V2 归因出的三大问题——覆盖不全、上下文膨胀、成本与延迟。

**做什么**

| 手段 | 对应问题 | 具体做法 |
|---|---|---|
| **反思回环** | 覆盖不全 | Critic 输出缺口清单，按缺口生成补充检索，最多 2 轮 |
| **上下文工程** | 上下文膨胀 | evidence 分块摘要入库，prompt 只带摘要+ID；按子问题聚合相关证据 |
| **并行检索** | 延迟 | 同层子问题 `asyncio.gather` 并发，带并发上限与超时 |
| **去重** | 成本 | 先 simhash / token Jaccard（**不引入向量库**），重复来源合并 |
| **模型分级路由** | 成本 | 小模型做抽取/摘要/去重判断，大模型只做规划与写作 |
| **预算管理** | 失控 | 每次调用前扣预算，余额不足强制收敛到 WRITE |

**技术栈**：+ asyncio 并发控制 · simhash/文本相似度 · 模型路由层 · 预算管理器 · 摘要缓存

**预期效果**：成功率 **70% → 78%**，平均步数 **15 → 11**，P95 **160s → 95s**，单次成本 **¥0.8 → ¥0.45**。

**面试怎么讲**：讲**权衡**而不是"我又加了功能"。核心论点：反思回环不是越多越好，第 3 轮收益趋近于零但成本线性上升，所以我设了 2 轮上限——这是"有界自主"的具体体现。

**DoD**：A/B 对比表（V2 vs V3 五项指标）；反思轮次消融实验（0/1/2/3 轮的收益曲线）。

---

### V4 · 可交付（2.5 人日）

**要解决的**：CLI 没法在面试里演示；跑 90 秒的长任务失败就得重来。

**做什么**

- FastAPI + SSE：把状态转移、工具调用、token 消耗实时推到前端
- 单页 UI（原生 JS + EventSource，无构建）：问题输入 → 实时步骤流 → 报告 + 可点击引用
- **checkpoint 恢复**：每步落库，进程被杀后可 `resume` 从断点继续
- 取消与中途介入：可取消、可追加子问题

**技术栈**：+ FastAPI · SSE · 状态快照重放 · 单页静态前端

**预期效果**：成功率 **78% → 80%**（断点恢复让失败任务可续跑，边际提升小，符合预期）。演示体验质变。

**面试怎么讲**：讲**产品化完成度**——"agent 不只是脚本，长任务必须有状态、可恢复、可中断"。这一条能显著区别于"跑个 notebook 截图"的候选人。

**DoD**：浏览器实时看到步骤；kill 进程后 `resume` 成功续跑；3 分钟 demo 一次过。

---

### V5 · 加分项（可选，2–3 人日）

**二选一，不要都做。**

**选项 A：多 Agent 对照实验**
supervisor + 三个专家 agent，与单 Agent 在同一套 50 题上对比。**必须给出结论**，哪怕是"多 Agent 成本 +80%、成功率只 +3%，所以不采用"——这个否定结论比硬吹多 Agent 更有说服力。

**选项 B：把评测 harness 抽成通用平台**
脱离本项目，能接入任意 agent（定义 trace 格式 + 打分器插件）。适合投平台/Infra 岗位。

**面试怎么讲**：只讲结论和证据，不讲"我用了某某多 Agent 框架"。

## 3. 指标轨迹（目标值，待实测回填）

| 指标 | V0 | V1 | V2 | V3 | V4 |
|---|---|---|---|---|---|
| 任务成功率 | 45% | 62% | 70% | 78% | 80% |
| 引用支持率 | 不可测 | 88% | 90% | 92% | 93% |
| 平均步数 | 18 | 16 | 15 | 11 | 11 |
| P95 耗时 | 180s | 170s | 160s | 95s | 95s |
| 单次成本(¥) | 0.9 | 0.85 | 0.8 | 0.45 | 0.45 |
| 崩溃率 | 高 | 0 | 0 | 0 | 0 |

**注意**：成功率 45%→80% 看起来陡，但其中约 15 个点来自"把之前悄悄失败的 case 纳入统计并修复"，只有约 20 个点是真实算法改进。面试时**主动说明这一点**，比让人以为你靠调 prompt 涨了 35 个点更可信。

## 4. 面试问题 → 由哪次迭代回答

| 面试官会问 | 你的答案来自 |
|---|---|
| 你的 agent loop 怎么实现的？ | V0 状态机（可画图、可讲状态转移条件） |
| 怎么防止死循环 / 成本失控？ | V1 四重终止 + V3 预算管理 |
| 幻觉引用怎么处理？ | V1 回填校验 + 降级标记（工程手段，非 prompt） |
| 怎么评测的？数据集哪来的？ | V2 50 题集 + judge 校准 |
| 失败率多少？失败集中在哪？ | V2 失败分布表 |
| 你怎么知道改动有效？ | V2→V3 的 A/B 对比 + 消融实验 |
| 为什么不做多 Agent？ | V5 选项 A 的对照数据 |
| 怎么上生产？ | V4 checkpoint/恢复 + 取消 + 审计式 trace |
| 延迟和成本怎么优化？ | V3 并行 + 摘要 + 模型路由（含数字） |

**结论**：V0–V4 做完，上表 9 个问题全部有实证答案。没有 V2，第 4–6 题全部答不上来——这就是为什么 V2 是分水岭。

## 5. 演示动线（面试现场）

**3 分钟版本**

1. 30 秒：一句话定位 + 指标表（"80% 成功率、引用可溯源、单次 4 毛"）
2. 90 秒：`RUN_MODE=mock` 跑一个问题，看 SSE 流式步骤（无网络也能跑）
3. 60 秒：打开一条失败 trace，讲归因和一个具体修复
4. 30 秒：打开评测报告，讲失败分布和下一步

**10 分钟版本**：加讲架构图、状态机、消融实验、以及"如果重做我会怎么改"。

## 6. 迭代纪律（防止项目烂尾）

1. **禁止无 trace 优化**：任何 prompt/策略改动，必须先指出 trace 里的证据，否则视为无效改动。
2. **每个版本打 tag + 写 README 章节**：`v0.1-baseline` / `v0.2-reliable` / …，让提交历史本身就是故事线。
3. **指标只认同一套题**：50 题集建好后冻结，新增题目单独开 `v2` 数据集，避免"换题涨分"。
4. **时间盒**：任一迭代超期 1 天，砍范围（先砍 UI，最后砍评测），绝不砍评测。

## 7. 时间总账

| 版本 | 工期 | 累计 |
|---|---|---|
| V0 | 2.5d | 2.5d |
| V1 | 3d | 5.5d |
| V2 | 3d | 8.5d |
| V3 | 3.5d | 12d |
| V4 | 2.5d | 14.5d |
| V5（可选） | 2–3d | 17.5d |

**最小可面试版本（V0–V2，8.5 人日）就能撑起一场面试**：有基线、有可靠性工程、有评测和失败归因。V3/V4 是把"能聊"升级成"能演示"。V5 是差异化。

如果你的时间只有一周，建议砍到 V0+V1+V2 的简化版（评测题减到 20 题），仍可讲清楚完整故事。
