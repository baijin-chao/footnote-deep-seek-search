# 挑战集

> 配套：[06-eval-design.md](06-eval-design.md)（评测框架）、[07-bugs.md](07-bugs.md) BUG-17（为什么要拆分）

---

## 1. 为什么需要两套题

回归集 `v1.jsonl` 的基线是 100%——它能防止退化，但**衡量不了优化收益**：分母已经顶到头了。

挑战集 `hard.jsonl` 的作用是提供**可提升的空间**：题目刻意设计成当前架构的薄弱点，
让 V3 的改动有可比较的余地。

| 集合 | 文件 | 定位 | 期望 |
|---|---|---|---|
| 回归集 | `eval/dataset/v1.jsonl` | 不能变差 | 保持 100% |
| 挑战集 | `eval/dataset/hard.jsonl` | 应该变好 | 60–80% |

两套分开报告，不能混算——混在一起会让"换题"变成涨分手段。

---

## 2. 设计原则：难在判据，不在冷门

题目**不是**挑生僻话题，而是让"看起来答完了"和"真的答对了"分开。四个方向：

| 难点类型 | 机制 | 例子 |
|---|---|---|
| **精确数字** | `must_cover` 绑死具体数值，错一个就不得分 | Llama 3 70B 的 15T token、8K 上下文 |
| **口径差异** | 要求指出数字的限定条件，只报一个数不给分 | DeepSeek-V3 的 557.6 万美元只含 GPU 租用 |
| **需要计算** | 要求做一步真实换算，复述数字无效 | 由成本与 GPU 小时反推每卡时价 |
| **前提有错** | 题目本身建立在错误假设上，正确行为是纠正 | 「GPT-5 用 10 万张 H100，依据是什么」 |

## 3. 题目清单（12 题）

| ID | 类别 | 考点 |
|---|---|---|
| `hard-fact-01` | 事实 | Llama 3 70B 的 token 数与上下文 |
| `hard-fact-02` | 事实 | 欧盟 AI Act 中 GPAI 义务的生效日 |
| `hard-fact-03` | 事实 | Llama 3.1 405B 的三项参数 |
| `hard-compare-01` | 对比 | Qwen2.5 与 Llama 3.1 的许可证差异 |
| `hard-compare-02` | 对比 | DeepSeek-V3 训练成本的不同口径 |
| `hard-compare-03` | 对比 | 专家并行（EP）与张量并行（TP）的区别 |
| `hard-fresh-01` | 时效 | Qwen 最新开源版本（须官方来源） |
| `hard-multi-hop-01` | 多跳 | 由训练成本反推每卡时价 |
| `hard-multi_hop-02` | 多跳 | V2→V3 参数与注意力机制变化 |
| `hard-multi_hop-03` | 多跳 | FlashAttention 与 PagedAttention 的区别 |
| `hard-no-answer-01` | 无解 | 「GPT-5 用 10 万张 H100」的错误前提 |
| `hard-no-answer-02` | 无解 | Llama 4 预训练数据构成未公开 |

分布：事实 3 / 对比 3 / 时效 1 / 多跳 3 / 无解 2。
时效只放 1 题，因为 `--no-cache` 会显著增加额度消耗。

## 5. 失败分析：两题都是「证据没找到」，不是「推理错了」

`hard-multi-hop-01` 的报告自己写得很清楚：

> 第二，GPU 小时数缺失。证据中没有出现 DeepSeek-V3 的训练卡数、训练天数或总 GPU 小时数……
> 分子 557.6 万美元有证据支撑，分母却完全缺失，因此无法得出数值。

**它的推理是对的，甚至主动指出了缺什么，但没有回头去补检索。**

这正是 V3 反思回环要解决的问题：Critic 发现"关键事实缺失"，触发一次针对性搜索
（比如直接把 `DeepSeek-V3 technical report GPU hours` 作为新查询），而不是止步于"证据不足"。

`hard-compare-01` 同理：拿到了 Qwen 的许可证信息，却没有拿到 Llama 3.1 的自定义许可条款。

## 6. 一个必须记录的观察：单轮结果不可靠

同一道 `hard-multi-hop-01`，两次运行：

| 运行 | 覆盖率 | 归因 |
|---|---|---|
| hard-baseline | 67% | fabricated（推算口径与官方不一致） |
| hard-v1 | 0% | uncovered（没找到 GPU 小时数） |

**同一题、同一模型、同一数据集，覆盖率从 67% 掉到 0%。**

原因很直接：每次运行拆出的子问题不同 → 检索到的页面不同 → 有时恰好命中关键页面，有时没有。

### 结论

1. **单轮数字不能用来判断"改进了 3 个百分点"**，那可能是检索运气
2. V3 的对比必须**至少跑 3 轮取均值**，并同时报告极差
3. 12 题的样本量下，1 题 = 8.3 个百分点，置信区间很宽

这条要写进 README，否则拿 83% 和 90% 对比就是在自欺。

## 7. 怎么用

```bat
REM 挑战集单轮
scripts\eval.cmd --dataset eval\dataset\hard.jsonl --tag v3-reflection

REM 时效题必须绕过缓存
scripts\eval.cmd --dataset eval\dataset\hard.jsonl --no-cache --tag fresh-check
```

**推荐流程**：改动前后各跑 3 轮，报告「均值 ± 极差」，而不是单次数字。

```bat
for /L %i in (1,1,3) do scripts\eval.cmd --dataset eval\dataset\hard.jsonl --tag before-%i
```

## 8. 已知局限

1. **题量小**：12 题，1 题 = 8.3 个百分点
2. **must_cover 由我编写**：可能带有"我知道答案才写得出来"的偏差
3. **时效题只有 1 道**：不足以评估新鲜度能力
4. **没有对抗样本**：比如"故意给出错误但看起来权威的来源"，这类才是真实场景里最危险的
