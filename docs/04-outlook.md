## 一、总体思路

这个项目要经过三级跳，每一级的验收标准不同：

| 阶段 | 目标 | 判定标准 | 对应版本 |
|---|---|---|---|
| **能跑** | 端到端出报告 | 有基线数据、有 trace | V0 ✅ |
| **能演示** | 面试现场 3 分钟讲完 | 断网也能跑、有可视化 | V4 |
| **能讲深** | 经得起追问 | 有评测、有失败归因、有取舍依据 | V2 + V5 |

浏览器界面属于"能演示"这一级，不是锦上添花——**面试时看命令行滚屏，和看一个实时推进的界面，说服力差一个量级**。

## 二、近期：V1 → V4

### V1 可靠性（3 人日）

引用回填校验（claim 与原文片段比对，不匹配降级为 `[未证实]`）、结构化输出加固、抓取失败降级、四重终止条件。

**可感知的变化**：报告末尾不再出现"引用了但没被正文用到"的条目，错误引用被标灰。

### V2 可观测与评测（3 人日）

span 树、失败分布、50 题评测集、一键跑批、LLM-judge + 人工校准。

**可感知的变化**：多了一个 `scripts\eval.cmd`，跑完输出一张指标表；能回答"成功率多少、失败集中在哪"。

### V3 智能化（3.5 人日）

反思回环（按缺口补检索）、上下文工程、并行检索、去重、模型分级路由、预算扣减。

**可感知的变化**：步数从 15 降到 11，成本腰斩，覆盖更全。

### V4 可视化（2.5 人日）← 本文重点

浏览器界面 + SSE 实时推送 + 断点恢复。

## 三、浏览器界面（V4 详细设计）

### 3.1 为什么值得做

1. **演示**：命令行滚屏观众看不懂；界面能一眼看出"Agent 在思考、在搜索、在写作"。
2. **可解释性**：每一步可展开、可回看，失败点可以直接指给面试官看。
3. **产品感**：这是"我做了个产品"和"我写了个脚本"的分界线。

### 3.2 页面结构

```
┌──────────────────────────────────────────────────────────────┐
│  Deep Research Agent                        [设置] [历史]     │
├────────────────┬────────────────────────────┬────────────────┤
│                │                            │                │
│  ① 提问区       │   ② 实时步骤流              │  ③ 证据面板     │
│                │                            │                │
│ ┌────────────┐ │  ● PLAN  完成 1.2s          │  [E1] 标题     │
│ │ 输入问题…   │ │    拆出 6 个子问题 ▾        │  来源域名       │
│ └────────────┘ │                            │  摘要…         │
│                │  ● SEARCH 进行中 2.5s       │  ────────────  │
│ 预算：25 步     │    ? 2026 年国产开源…       │  [E2] 标题     │
│ 上限：¥0.6     │    ← 8 条结果               │  …             │
│                │                            │                │
│ [开始研究]      │  ● FETCH 完成 0.9s          │                │
│ [取消]         │    采纳 3 篇正文 ▾          │                │
│                │                            │                │
├────────────────┴────────────────────────────┴────────────────┤
│  ④ 报告区：流式产出 Markdown，[E3] 可点击高亮对应证据          │
├──────────────────────────────────────────────────────────────┤
│ ① 进度条  ████████░░ 62%   ¥0.021 / 0.6   37s / 120s         │
└──────────────────────────────────────────────────────────────┘
```

### 3.3 交互流程

```
用户输入问题
   │
   ├─▶ POST /api/runs            → 立刻返回 run_id（不阻塞）
   │
   ├─▶ GET  /api/runs/{id}/events（EventSource 长连接）
   │      每发生一个状态转移就推一条事件
   │
   ├─▶ 前端按事件类型渲染：state 卡片 / 计划列表 / 证据条目
   │
   └─▶ done 事件 → 渲染报告，引用变成可点击的锚点
```

关键点：**后端不等待**。POST 立即返回，任务在后台跑，前端靠 SSE 追进度。这样刷新页面也能接上（重新订阅即可，因为状态在 SQLite 里）。

### 3.4 技术方案

| 部分 | 选型 | 理由 |
|---|---|---|
| 后端 | FastAPI + `sse-starlette` | 已装 fastapi；SSE 比 WebSocket 简单 |
| 前端 | 单文件 HTML + 原生 JS + EventSource | 零构建、零 npm、断网可开 |
| 样式 | 手写 CSS（约 200 行） | 不引入 Tailwind，避免构建链 |
| 状态 | 后端 SQLite 为唯一真相 | 刷新/重连不丢进度 |

### 3.5 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/runs` | 入参 `{question, max_steps?, max_cny?}`，返回 `{run_id}` |
| `GET` | `/api/runs/{id}/events` | SSE 流，事件见 3.6 |
| `GET` | `/api/runs/{id}` | 当前快照（刷新页面用） |
| `GET` | `/api/runs/{id}/evidence` | 证据列表 |
| `GET` | `/api/runs/{id}/report` | Markdown 报告 |
| `POST` | `/api/runs/{id}/cancel` | 取消 |
| `GET` | `/api/runs` | 历史列表 |

### 3.6 SSE 事件协议

与内部 `emit()` 一一对应，前端只认这几种：

| event | data | 前端表现 |
|---|---|---|
| `run_started` | `{run_id, question}` | 清空面板，显示"开始" |
| `state` | `{state, steps}` | 新增一条状态卡片 |
| `plan` | `{questions: []}` | 展开子问题清单 |
| `search` / `search_done` | `{question}` / `{results}` | 显示进度与条数 |
| `read_done` | `{docs}` | 显示采纳篇数 |
| `reflect` | `{evidence_count}` | 显示证据总数 |
| `done` | `{stats, report, citations}` | 渲染报告，点亮引用 |
| `error` | `{message}` | 红色提示 |

### 3.7 工作量拆解

| 任务 | 工时 |
|---|---|
| FastAPI 骨架 + SSE 推送 + 后台任务 | 0.5d |
| 快照接口 + 取消 + 历史列表 | 0.5d |
| 单页 UI（三栏 + 状态卡片 + 引用高亮） | 1d |
| 断点恢复（进程重启后续跑） | 0.5d |
| **合计** | **2.5d** |

### 3.8 演示脚本（面试现场，3 分钟）

1. 输入一个时效性问题，点开始
2. 界面实时推进：规划出 6 个子问题 → 搜索 → 抓取 → 反思 → 写作
3. 中途点开某一步，展示耗时与 token
4. 报告出来后，点 `[E3]` 跳到对应证据，展示"引用可溯源"
5. 切到 trace 面板，指着一条失败 span 讲归因

> 断网兜底：演示前用 `--mode record` 录一次，现场切 `mock` 回放。

## 四、中期可做（3–6 个月视野）

| 方向 | 内容 | 价值 |
|---|---|---|
| **成本优化** | 语义缓存（相同子问题复用）、检索结果缓存、输出长度自适应 | 单次成本再降 30–50%，可讲"单位经济" |
| **并发与吞吐** | asyncio 全异步 + 任务队列（Redis）+ 限流 | 从"一次一个"到"多人同时用" |
| **多源搜索** | Tavily / 博查 / 自建 SearXNG / arXiv / 官方文档源 | 提升覆盖，也是降级链的延伸 |
| **文档解析** | PDF、PPT、Excel（接入本地解析，不依赖第三方） | 从"网页研究"扩展到"资料研究" |
| **多轮追问** | 在已有报告上继续问，复用证据库 | 接近真实研究流程 |
| **增量更新** | 同一问题定期重跑，diff 出新变化 | 可做成"行业监控"产品 |

## 五、长期/加分项

### 5.1 多 Agent 对照实验（V5，2–3 人日）

不是"上多 Agent"，而是**证明多 Agent 值不值**。同一套 50 题，比较：

| 方案 | 成功率 | 成本 | 延迟 |
|---|---|---|---|
| 单 Agent（现状） | 78% | ¥0.45 | 95s |
| Supervisor + 3 专家 | ? | ? | ? |

结论哪怕是"多 Agent 成本 +80%、成功率 +3%，不划算"，也比硬吹有价值——**这是工程判断力**。

### 5.2 评测平台化（V5 备选，2–3 人日）

把评测 harness 抽出来，定义通用 trace 格式 + 可插拔打分器，能接入任意 agent。适合投平台/Infra 岗。

### 5.3 MCP 工具生态

把搜索、抓取、报告导出封装成 MCP server，让 Claude/Cursor 等外部 agent 直接调用。这是 2026 年的生态趋势，成本低、话题性好。

### 5.4 部署与运维

Docker 化（当前机器未装 Docker）、健康检查、日志聚合、灰度发布、按 run 的审计日志。
企业场景还需要：权限控制（谁能看哪份报告）、数据脱敏、成本配额。

### 5.5 安全加固

- **提示注入**：网页内容里可能藏指令，必须当作数据而非指令处理
- **SSRF**：禁止抓取内网地址（`127.0.0.1`、`10.x`、`192.168.x`）
- **内容合规**：输出侧过滤
- **密钥管理**：`.env` → 密钥服务

> 这几条现在没做，但**能说出来**本身就是加分项。面试官很爱问"如果上线你会补什么"。

## 六、明确不做

保持克制同样重要，这些是主动放弃的：

| 不做 | 原因 |
|---|---|
| 通用聊天助手 | 已被大厂做透，没有差异化 |
| Computer Use / 浏览器操作 | 演示不稳定，失败率高，风险大于收益 |
| 自研向量数据库 | 不是本项目要证明的能力 |
| 复杂前端框架 | 收益不匹配构建成本 |
| 追求"全自主" | 有界自主才是工程现实，也更好讲 |

| 可用时间 | 交付 | 能撑住什么 |
|---|---|---|
| 3 天 | V0 + V1 | 能讲清 agent loop 与可靠性工程 |

## 八、面试时怎么讲"展望"

三条原则：

1. **先讲判断，再讲功能**。不说"我要加个 Web 界面"，说"命令行无法证明 Agent 在工作，界面解决的是可解释性问题"。
2. **每个展望都带成本和收益**。"多 Agent 要多花 80% 成本，所以我要先做对照实验再决定"。
3. **承认边界**。主动说"提示注入和 SSRF 我现在没做，上线前必须补"——比被问出来强得多。

一个可用的收尾句式：

> 这个项目现在能证明三件事：Agent 的循环我能自己实现、失败我能定位、改进我能量化。剩下的都是在这三个能力上加东西——加界面、加并发、加工具生态，但底层方法论不变。
