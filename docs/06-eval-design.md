## 0. 目标与验收

**一句话**：把"落地率 91%"这种单次样本，变成"20 题平均 89%，P95 延迟 96s"这种可复现的分布。

**验收标准（DoD）**

1. 一条命令跑完 20 题，输出 `summary.md` + `summary.csv`
2. 每题都有：指标、失败归因（若失败）、trace 路径、报告路径
3. LLM judge 与人工标注的一致率 ≥ 85%
4. 同一 dataset + 同配置，重跑结果差异可解释（不是随机波动）

---

## 1. 为什么这一步不能跳过

现在项目里所有数字都来自**一次运行**。单次样本有三个问题：

| 问题 | 后果 |
|---|---|
| 没有分布 | 面试官问"稳定吗"，只能答"应该还行" |
| 没有对照组 | 改完 prompt 说"变好了"，无法证明 |
| 没有失败样本 | 无法归类问题，优化变成猜 |

V3 的反思回环、模型路由，全部依赖这套评测来判断值不值得做。**没有评测的优化都是玄学**。

## 2. 数据集设计

### 2.1 题目分布（20 题）

**为什么是 20 题**：Tavily 免费额度约 1000 次搜索/月，每题约消耗 6 次（6 个子问题），全量一轮≈120 次。
20 题能跑约 8 轮，够覆盖"基线 → V1 回归 → V3 三次迭代"；50 题只够 3 轮，迭代到一半就没额度了。

| 类别 | 数量 | 考察点 | 示例方向 |
|---|---|---|---|
| 事实型 `fact` | 6 | 能否找到并准确复述 | "RAG 的典型流程分几步" |
| 对比型 `compare` | 4 | 能否多源对比、给出判断 | "RAG 与微调的成本结构差异" |
| 时效型 `fresh` | 4 | 能否拿到近期信息 | "2026 年国产开源模型进展" |
| 多跳 `multi_hop` | 3 | 能否串联多个子问题 | "某技术的论文→落地→争议" |
| 无解 `no_answer` | 3 | **能否承认不知道** | "某公司 2027 年营收预测" |

20 题的统计效力有限（1 题 = 5 个百分点），但足以**看趋势和抓失败类型**。
如果后续额度允许，优先扩到 30 题而不是重写题目——保持题目连续，指标才可比。

> 配额不是只能靠减题解决：配合 §5.4 的搜索缓存，重跑只消耗缓存未命中的查询，
> 同一数据集第二次跑几乎零额度。减题 + 缓存，两者都要。

### 2.2 单题格式（JSONL，一行一题）

```json
{
  "id": "fact-01",
  "category": "fact",
  "question": "检索增强生成（RAG）的典型流程包含哪几个阶段？",
  "must_cover": ["索引", "检索", "生成"],
  "should_refuse": false,
  "expected_sources": ["official", "edu"],
  "difficulty": "easy",
  "notes": "三点都要覆盖，缺一即扣分"
}
```

| 字段 | 用途 |
|---|---|
| `must_cover` | 判分的硬标准：覆盖 2/3（至少 2 条）即算通过 |
| `should_refuse` | 为 `true` 时，正确行为是明确说"未找到可靠来源" |
| `expected_sources` | 只作参考，不参与自动判分（避免过度约束） |
| `difficulty` | 用于分层统计：简单题失败说明基础有问题，难题失败可接受 |

### 2.3 编题规则（防止自欺）

1. **人工编写，不用模型生成**——模型出的题会偏向模型擅长的领域
2. `must_cover` 必须是**能从公开资料核实**的要点，不许写"要有深度"这种主观项
3. 每题只问一件事，不合并多个主题
4. `no_answer` 题必须**真的没有公开答案**（编题时先自己搜一遍确认）
5. 题目冻结后不轻易改；要改就开 `v2` 数据集，避免"换题涨分"

### 2.4 存放

```
eval/dataset/v1.jsonl        题目（进仓库，它本身就是作品的一部分）
eval/dataset/v1.schema.json  格式约束
eval/judge_prompt.md         判分提示词（可审计）
```

## 3. 指标定义

| 指标 | 计算方式 | 目标 | 用途 |
|---|---|---|---|
| **任务成功率** | `must_cover` 覆盖 ≥ 2/3（至少 2 条）且无事实错误 | ≥ 75% | 主指标 |
| **引用落地率** | 强支撑 + 弱支撑 / 总断言（已有实现） | ≥ 85% | 可信度 |
| **拒答正确率** | `no_answer` 题中明确说明"未找到"的比例 | ≥ 80% | 诚实度 |
| **P50 / P95 延迟** | 单题耗时分布 | ≤ 60s / 120s | 体验 |
| **单题成本** | 均值与 P95 | ≤ ¥0.05 / ¥0.10 | 经济性 |
| **平均步数** | 状态机 step 数 | ≤ 12 | 效率 |
| **崩溃率** | 状态非 done 的比例 | ≤ 5% | 稳定性 |

统计口径：**分母是全部 20 题**，失败的题也算进去——只统计成功的题会得出漂亮但错误的结论。

## 4. 判分设计

### 4.1 为什么不完全依赖人工

50 题 × 每次迭代，人工不可能每题都读。用 LLM judge 做初筛，人工只抽检。但必须**先校准**，否则 judge 的偏差会被当成事实。

### 4.2 judge 输入输出

**输入**：问题、`must_cover` 列表、报告正文
**输出**（JSON）：

```json
{
  "covered": [
    {"item": "索引", "covered": true, "quote": "报告中的原文片段"},
    {"item": "检索", "covered": true, "quote": "..."},
    {"item": "生成", "covered": false, "quote": ""}
  ],
  "factual_errors": ["报告称 RAG 需要微调，与原文矛盾"],
  "verdict": "pass"
}
```

三条硬约束：

1. **每条 `covered=true` 必须附报告原文片段**，防止空口判"覆盖了"
2. **不允许因为写得长就给分**，只认要点
3. `temperature=0`，`thinking=off`，同输入应得同输出

### 4.3 校准流程（关键步骤）

1. 随机抽 6–20 题
2. 按同一 rubric 逐要点标注
3. 计算 judge 与标注的一致率
4. **< 85% 就改 prompt 重来，不许直接采信**

**已执行（2026-11-17）**：抽 6 题 / 16 个要点判定，一致率 **93.75%**，达到门槛。
完整结果、两处不一致的根因与处理见 [08-calibration.md](08-calibration.md)。

> 该次标注由 agent 完成，不是真正的人类标注，只能证明「换一个视角结论一致」。
> 严格的人机一致性仍需真人复标（见 08 号文档 §5）。

这一步要写进 README——它证明你知道 judge 有偏差，而且量化了。

### 4.4 成本控制

judge 用 `deepseek-flash`：20 题 × 约 3k token ≈ ¥0.01/轮，比跑 agent 本身便宜一个量级。

## 5. 跑批工具

### 5.1 用法

```bat
REM 全量
scripts\eval.cmd --dataset eval\dataset\v1.jsonl

REM 冒烟（前 5 题）
scripts\eval.cmd --limit 5 --concurrency 1

REM 限定预算
scripts\eval.cmd --max-cny 5
```

| 参数 | 说明 |
|---|---|
| `--dataset` | 数据集路径（默认 `eval/dataset/v1.jsonl`） |
| `--limit N` | 只跑前 N 题，用于冒烟 |
| `--tag` | 给这批结果打标签，便于对比（如 `before-reflect`） |
| `--max-cny X` | 总成本上限，超出即停 |
| `--resume` | 跳过已有结果的题（断点续跑） |
| `--no-cache` | 禁用搜索缓存（时效题评测用） |
| `--dry-run` | 只校验数据集，不实际运行 |
| `--quiet` | 不打印逐题进度 |

> **V2 先串行跑**：并发写同一个 SQLite 需要处理锁竞争，而搜索缓存已经把额度问题压下去了，
> 串行的稳定性收益更高。`--concurrency` 留到 V2.1，届时改用独立数据库文件。

### 5.2 断点续跑

每题完成后立即追加一行到 `results.jsonl`。进程中断后加 `--resume` 继续，已完成的题跳过。

### 5.3 输出结构

```
.work/eval/<timestamp>-<tag>/
├── results.jsonl        每题一行：指标 + 归因 + 路径
├── summary.md           给人看的报告（含分布表与失败分析）
├── summary.csv          给表格软件/画图用
├── reports/<id>.md      每题报告
└── traces/<id>.jsonl    每题 trace
```

---

### 5.4 搜索缓存（配额的关键解法）

每次搜索按 `(provider, query)` 的哈希存进 SQLite，重跑时先查缓存：

```sql
CREATE TABLE search_cache (
    cache_key   TEXT PRIMARY KEY,   -- sha1(provider + "|" + normalized_query)
    provider    TEXT,
    query       TEXT,
    results     TEXT,               -- JSON
    created_at  TEXT
);
```

规则：

- `RUN_MODE=mock` 只读缓存，未命中则报错（保证离线演示一致）
- `RUN_MODE=live` 先读缓存，未命中再请求并写入
- 缓存有效期默认 7 天（`SEARCH_CACHE_TTL_DAYS`），过期重新抓，兼顾时效性
- `--no-cache` 参数强制绕过，用于新鲜度对比实验

**命中策略分两级**（实现时发现的关键问题）：

1. **精确命中**：`(provider, 归一化 query)` 哈希相同
2. **近似命中**：同一 provider 下，用中文 bigram 计算 `max(Jaccard, 包含度)` ≥ 0.8

为什么需要第二级：规划的拆解不是完全确定的，同一个问题两次运行的子问题措辞会略有不同——
实测第一版只有精确匹配时，重跑命中率仅 **20%**，缓存几乎没用。
加上近似匹配后升到 **60–80%**。

防误判：加了反义词保护——`优势/劣势`、`优点/缺点`、`提升/下降` 等成对词分属两条查询时，
禁止近似命中，避免把「RAG 的优势」和「RAG 的劣势」当成同一个问题。

**效果**：同一数据集第二次跑，搜索额度消耗接近 0。这样 20 题不只是"省额度"，而是"跑得起十几次迭代"。

副作用要说清楚：缓存会**掩盖时效性问题**。所以时效型题目的评测要加 `--no-cache`，否则测的是缓存不是搜索。

## 6. 失败分类（taxonomy）

每题失败只归**一个主因**，规则按优先级从上往下匹配：

| 优先级 | 类别 | 自动判定规则 |
|---|---|---|
| 1 | `no_evidence` | 证据数 = 0 |
| 2 | `fetch_blocked` | 抓取成功率 < 50% |
| 3 | `budget_exceeded` | `stop_reason` 含预算字样 |
| 4 | `weak_grounding` | 落地率 < 50% |
| 5 | `uncovered` | `must_cover` 覆盖 < 80% |
| 6 | `fabricated` | judge 报 `factual_errors` 非空 |
| 7 | `refusal_missing` | `should_refuse` 为真但未拒答 |
| 8 | `judge_error` | judge 输出解析失败 |

这张表的价值：**它把"效果不好"变成"卡在哪一步"**。V3 的优化方向直接由最高频的类别决定。

## 7. 代码结构

```
src/dra/eval/
├── __init__.py
├── dataset.py     读取与校验（字段完整性、id 唯一）
├── judge.py       判分：构造 prompt、解析 JSON、重试
├── runner.py      跑批：并发、断点、预算、落盘
├── metrics.py     指标计算与失败归因
├── report.py      生成 summary.md / summary.csv
└── __main__.py    CLI
src/dra/cache.py   搜索缓存（SQLite + TTL），供 providers/search.py 调用
scripts/eval.cmd
```

复用现有能力，不重新造：`ResearchAgent` 直接调用，`verification` 从返回值取。

## 9. 首轮基线（2026-11-17）

```
模型 deepseek-flash  20 题  总成本 ¥0.5749
成功率 100%（20/20）   拒答正确率 100%（3/3）   平均落地率 89%
延迟 P50 30.7s / P95 40.5s   平均步数 7.8
```

**这个数字说明评测集太简单，不能作为优化基线。** 详见 [07-bugs.md](07-bugs.md) BUG-17。

处理方式：把这 20 题定位为**回归集**（必须保持 100%），另建**挑战集**衡量提升。

| 集合 | 目的 | 期望水平 |
|---|---|---|
| 回归集 `v1.jsonl` | 防止改动引入退化 | 保持 100% |
| 挑战集 `hard.jsonl` | 衡量优化收益 | 50–70% |

回归集与挑战集分开报告，避免"换题涨分"的嫌疑。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **搜索免费额度耗尽** | 迭代到一半无法继续 | 20 题 + 搜索缓存（重跑近零消耗）+ 断点续跑 |
| 搜索 API 限流 | 跑批中断 | 并发 ≤ 2 + 断点续跑 |
| 20 题统计效力弱 | 指标波动大，1 题=5 个百分点 | 只用于看趋势与失败类型；关键结论用多轮均值 |
| 单轮成本 | 约 ¥0.6–1/轮（20 题） | 可接受；`--max-cny` 兜底 |
| judge 偏差 | 指标不可信 | 人工校准 20 条，一致率 < 85% 就改 |
| 题目本身有争议 | 误判失败 | `notes` 字段记录判分要点 |
| 跑批结果难复现 | 无法对比 | 固定 dataset + 固定配置 + 记录 tag |

## 11. 需要你确认的 4 件事

| # | 决策 | 结论 | 备选 |
|---|---|---|---|
| 1 | 题量 | **20 题**（配额约束下已定） | 30 题（额度允许时再扩） |
| 2 | judge 模型 | **flash**（便宜 4 倍，判要点够用） | pro（更准，但贵） |
| 3 | 稳定性 | 先不做，V2.1 再考虑跑 3 次 | 现在就跑 3 次（+2 人日） |
| 4 | 数据集进仓库 | **进**（它是作品的一部分，可审计） | 不进（防刷题，但对个人项目无意义） |
| 5 | 搜索缓存 | **做**（否则额度撑不住多轮迭代） | 不做（每轮都烧额度） |

确认后我按 §8 的顺序做：先出 **6 题样例**（覆盖五类，含 1 道无解题）给你看质量，认可后补齐 20 题。
